# 面试准备：面试官会怎么看这个项目

> 本文以**面试官视角**写：他先怀疑什么、在哪里挖坑、什么答案算过关。
> 项目自述见 README；本文只讲"被问到时怎么答"。

---

## 一、先搞清面试官的心态

### 他看到简历时的第一反应

> "又一个 AI 项目。**是不是调个 API 拼个 prompt？**"

**这是默认假设。** 你要做的不是陈述功能，而是**用证据推翻它**。

### 他会用三个层次验证

| 阶段 | 时长 | 他在验证什么 | 失败的信号 |
|---|---|---|---|
| **① 是不是编的** | 30 秒 | 有没有真跑起来、真上线 | 说不出部署细节、答不出线上现象 |
| **② 架构合不合理** | 3~5 分钟 | 选型有没有理由、边界清不清楚 | 只会说"我用了 X"，说不出"为什么不用 Y" |
| **③ 边界与取舍** | 10 分钟 | 遇过什么问题、怎么定位、为什么这么修 | 说"没遇到过问题"或问题都是别人解决的 |

### 他真正想招的是什么人

**不是"会用 LangGraph 的人"，是"能在约束下做对取舍的人"。**

所以下面这些回答方向**比功能列表重要**：
- "我试过 A，失败了，因为……最后选了 B" ✅
- "这个我**故意没做**，因为……" ✅
- "这里有个坑，我用测试锁住了，不然会复发" ✅

## 二、30 秒电梯陈述（先练这一句）

> "一个**企业售后智能体**：用户在飞书里用一句话说需求，它自己判断该干什么 ——
> 查知识库、报修建单、自动派单、走退款审批；判断不了或风险高的时候，
> **中断等人确认**，或者**转给真人客服**，坐席认领后 AI 主动静默。
> 已经部署上线在跑，19k 行代码、112 个接口、288 个测试。"

**为什么这样开场**：
- "**自己判断该干什么**" = Agent（不是问答）
- "**中断等人确认 / 转给真人**" = 有边界（这是最强的差异化）
- "**已上线 + 数字**" = 不是玩具

**不要**开场就报技术栈 ✗ 那是第二步的事。

## 四、亮点梳理（三层，按"抗追问强度"排序）

### 第一层：业务闭环 —— 最抗追问

> 大多数 AI 项目到"回答一段话"就结束了。你的是**能改系统状态**。

| 亮点 | 一句话 |
|---|---|
| **真的办事** | 建工单、按技能/在线/负载三级派单、走退款审批 —— 不是回文本 |
| **转人工不是假的** | 工单化接管 + 坐席认领 + **AI 完全静默** + 结束转回 AI + 超时兜底 |
| **线索自动捕获** | 从飞书原话提手机号/公司名 → 建线索 → **分配销售** → 阶段/报价/成交自动留痕 |

**为什么最抗追问**：这些是**别人项目里通常没有的东西** ✗ 面试官一旦发现你有，注意力会从"是不是套壳"转到"这个怎么实现的" ✓

### 第二层：技术深度

| 亮点 | 关键点（被追问时要能展开） |
|---|---|
| **确定性编排 + 局部自主** | LangGraph 15 节点、4 个路由决策点、规则先行 RAG 兜底、两条 LLM-free 快路径 |
| **双过滤拒答** | 阈值 **或** 实体词覆盖才放行；答不上来**明确拒答转人工**，不编 |
| **RAG 反思与重试** | 第一轮同义词扩展，没过阈值时**用只保留故障码/型号的聚焦查询再试一轮** |
| **HITL 断点恢复** | `interrupt()` 挂起 → 状态落 SQLite → `Command(resume=)` 恢复，**跨进程重启不丢** |
| **自研意图与规则引擎** | YAML 可热加载、命中结果可解释，**刻意不用 LangChain 的 Agent 抽象** |

### 第三层：工程落地 —— 证明"真的上线了"

| 亮点 | 数字 |
|---|---|
| 部署在 **2GB 单机**，与另一个项目共存 | 实测常驻 **161 MiB** |
| 接口鉴权覆盖 | **112 个接口** / **27 个权限点** / 4 角色 |
| 测试 | **288 个用例**，多数是**线上故障换来的回归** |
| 代码量 | 19,378 行，`clone_check` 通过 |

## 五、技术栈"如何执行"（每个都要能答"为什么"）

面试官问技术栈不是为了听清单，而是**每个选择背后的理由**。

| 技术 | 你用它做了什么 | **为什么不用替代品**（这才是问题） |
|---|---|---|
| **LangGraph** | 显式状态机：15 节点 + 条件边 + Checkpointer | ❌ LangChain AgentExecutor：隐式循环不可控、无 interrupt/checkpoint。我只用它的 embedding 客户端 |
| **FastAPI** | 112 接口、异步、依赖注入做鉴权 | 相比 Flask：原生 async + Pydantic 校验 + 自动 OpenAPI |
| **SQLite + WAL** | 主库 + LangGraph checkpoint | 2GB 内存换取舍：省下 MySQL+Redis 约 700MB；SQLAlchemy 抽象，改环境变量可切 MySQL |
| **内嵌 Chroma** | 向量检索 | 相比 Milvus/Qdrant：省约 250MB + 少一个进程；数据量上来再换 |
| **jieba + rank-bm25 + 向量** | 双路召回 + RRF 融合 + 余弦精排 | 纯向量对**故障码/型号**这种精确串不敏感；BM25 补齐 |
| **LangGraph Checkpoint(SQLite)** | HITL 断点 | 内存 Saver 重启就丢；HITL 必须跨进程持久化 |
| **Docker Compose** | 单容器 prod + 前端构建服务 | 没用 K8s：单机 2GB，K8s 本身就要吃掉一半内存 |
| **Nginx + Let's Encrypt** | 反代 + HTTPS + 证书自动续期 | 复用服务器已有 nginx，不引入 Caddy |
| **pytest** | 288 用例 | 特别针对**图路由完整性**和**会话线程映射**做了回归 |

**回答模板**：
> "我选 X，因为 [场景约束] → [X 的某个特性] 恰好匹配。
> 我**考虑过 Y**，但 Y 的问题在 [具体问题]，代价我接受不了。"

## 六、Agent 体现在哪（这题几乎必问）

### 直接回答：四个层面

```
① 自主判断该做什么   → 意图 + 规则引擎决定路由（用户不选菜单）
② 自主执行真实动作   → 建单/派单/退款/通知（真的改系统状态）
③ 自主判断"我做不了"  → 双过滤拒答 → 转人工 / HITL
④ 知道何时交给人     → interrupt 断点 → 人工确认 → 原状态恢复
```

**核心一句话**：Chatbot 输出**文本**，你的系统输出**动作和状态变化**。

### 标准答法（背下来）

> "Agent 的核心不是'用了大模型'，而是**自主决策 + 真实执行 + 知道自己边界**。
>
> **第一，自主判断。** 用户不选功能，一句话进来，系统靠意图引擎和 4 个路由函数
> 自己决定是检索、建单、退款还是转人工。而且我做了策略选择：
> **规则能解决的绝不调模型** —— 更快、更准、省 token。
>
> **第二，真的办事。** 报修会自动建工单并按技能、在线、负载三级排序派单；
> 退款走风控评分，低风险自动执行、其余转审批。它改的是真实数据。
>
> **第三，知道什么时候该停。** 检索不到时**明确拒答而不是编造**；
> 高风险动作 `interrupt()` 挂起等人工确认，状态落 SQLite，
> 跨进程重启都能恢复；用户要人工时，坐席一认领 **AI 就完全静默**。
>
> **我也清楚边界**：没做成 LLM 自由选工具，而是确定性状态机编排 ——
> 因为售后要求可解释、可审计、可测试。这是取舍，不是能力缺失。"

### 追问"那你做到 multi-agent 了吗"

**答"没有"，但要答得像是主动决策**：

> "没有，我是**有意识地没做**。多 agent 的价值在开放式任务里让多个角色互相校验；
> 但售后场景**流程边界清晰、动作有明确对错** —— 退款退多少必须是规则算出来的，
> 不能是某个 agent 感觉出来的。硬拆只会带来不可预测性和调试成本。
>
> 不过我有两个**真正的多体协作**：
> 一个是 **HITL** —— 高风险动作挂起等人决策再恢复；
> 另一个是**转人工** —— 坐席认领后 AI 完全静默，处理完再转回来，
> 本质上是一次 **AI 向人的完整交接**，包括把所有上下文交过去。
>
> 我觉得这比'两个 LLM 互相聊天'更接近生产里真正需要的东西。"

## 七、面试官可能问的问题（按被问概率排序）

### A. 开场与真实性（100% 会问）

1. **"简单介绍一下这个项目"** → 用 §2 的 30 秒版
2. **"上线了吗？部署在哪？"** → 2GB 阿里云单机，Docker，nginx + HTTPS，与另一个项目共存
3. **"你自己一个人做的？"** → 是，从需求到部署
4. **"做了多久？"** → 如实说，别说"三个月做了 19k 行"（不可信）
5. **"数据是真的吗？"** → 业务数据是模拟生成的，代码和架构是真的

### B. 架构与选型（90%）

6. **"为什么用 LangGraph 不用 LangChain Agent？"** → 隐式循环不可控、无 interrupt/checkpoint
7. **"为什么不用 AutoGen / CrewAI？"** → 单 agent 流程确定，多 agent 框架的价值用不上
8. **"为什么规则引擎在 RAG 前面？"** → 确定性优先：更快更准可解释省 token
9. **"15 个节点怎么划分的？"** → 按业务动作，不是按技术层
10. **"为什么不用 MySQL / Redis？"** → 2GB 内存取舍，SQLAlchemy 可切换
11. **"为什么内嵌 Chroma 不用 Milvus？"** → 省 250MB + 少一个进程
12. **"向量库数据量大了怎么办？"** → 换独立向量服务，检索接口不变

### C. RAG（90%）

13. **"混合检索怎么做的？"** → jieba+BM25 ∥ 向量 → RRF 融合 → 余弦重排
14. **"为什么 RRF 而不是加权求和？"** → 两路分数量纲不同，RRF 只看排名更鲁棒
15. **"父子块切片是什么？"** → 子块检索精准、父块给完整上下文
16. **"怎么防幻觉？"** → **双过滤拒答**：阈值 or 实体词覆盖，否则明确拒答
17. **"检索不到怎么办？"** → ⭐ **反思与重试**（见下）
18. **"怎么评估 RAG 效果？"** → 有 `rag_eval` 脚本；如实说没有建立完整评测集（**软肋**）
19. **"embedding 用的什么？"** → 可插拔：本地 BGE-M3 / 云端 DashScope

**第 17 题是加分题，一定要答好**：

> "我先试了**去停用词**，两版都不行：`str.replace` 把'怎么办'切成'办'；
> 改用 jieba 按整词过滤，'还是不行是什么原因'基本没删掉什么。
> **根本问题是中文停用词表永远补不全**，漏一个就产出比重试前更差的查询。
>
> 最后改成**只保留实体词** —— 故障码和型号。这类词能被正则可靠识别，
> 不依赖词表；而且恰好是检索失败时最该聚焦的东西：
> **问句越长，`E102` 这种短代码越容易被 BM25 的词频淹没。**
>
> 还加了边界：**没有实体词就不重试**，不硬凑查询也不白跑 embedding。"

### D. HITL（80%）

20. **"interrupt 怎么用的？"** → 挂起 → 状态落 SQLite → resume 恢复
21. **"进程重启了会怎样？"** → **断点还在**，这是用 SqliteSaver 而不是内存 Saver 的原因
22. **"哪些动作需要人工确认？"** → 退款、改派等高风险动作 + 低置信度
23. **"报修为什么不也全部走人工确认？"** → ⭐ **这是个坑，见 §8**
24. **"人工一直不处理怎么办？"** → 超时取消

### E. 转人工 / 线索（70%，你的差异化）

25. **"转人工怎么实现的？"** → 工单化接管 + 飞书通知坐席 + 认领
26. **"AI 怎么知道该闭嘴？"** → 坐席认领后置状态，入口层直接短路返回
27. **"坐席忘了点结束怎么办？"** → ⭐ **闲置 4 小时自动结束**（真实踩过：会话被永久静音）
28. **"AI 静默返回什么？"** → ⭐ **不能返回空串**（网关会判为生成失败），用零宽空格
29. **"线索怎么自动分配？"** → 销售岗优先 → 进行中线索最少 → 编号靠前
30. **"重复消息会建多条线索吗？"** → 幂等：同一会话未结束的线索会复用

### F. 工程与部署（70%）

31. **"2GB 怎么塞下的？"** → SQLite 替 MySQL、内嵌 Chroma、单 worker、日志轮转
32. **"内存超了会怎样？"** → OOM Kill，配了 mem_limit，swap 已开
33. **"怎么排查线上问题？"** → 结构化日志 + 审计表 + 通知记录表
34. **"有没有监控告警？"** → ❌ 没有，只有日志（**主动承认**）
35. **"升级怎么做的？"** → git pull + 重建镜像；如实说**没有灰度**
36. **"数据怎么备份？"** → 提醒：SQLite 是单文件，**目前是手工备份**（**软肋**）

### G. 权限与安全（60%）

37. **"鉴权怎么做的？"** → 双轨：后台 JWT + 权限点；网关共享 API Key
38. **"权限点怎么设计的？"** → 按操作细分，能看不等于能改；27 个点 × 4 角色 + 按人覆盖
39. **"权限改了要重新登录吗？"** → 不用，**每次请求从库里重算**
40. **"密钥怎么管的？"** → 全在 `.env`，**不进仓库**；提交前有敏感值扫描
41. **"有 SQL 注入 / XSS 风险吗？"** → 用 ORM 参数化；**如实说没做渗透测试**

### H. 测试与质量（60%）

42. **"测试覆盖了什么？"** → 意图/规则/切片/鉴权/工单/线索/转人工/图路由/线程映射/HITL
43. **"为什么专门测图路由？"** → ⭐ **漏登记条件边映射表导致线上 500**
44. **"测试是真能抓到 bug 吗？"** → ⭐ **会撤掉修复验证测试失败**（举 RAG 拒答那个例子）
45. **"有没有测试反而锁死了 bug？"** → ⭐ **有过**：一条测试断言"故障码兜底成型号"，把 bug 当成正确行为保护了

### I. 压力问题（必须准备）

46. **"这不就是调 API 吗？"** → 见 §9
47. **"AI 部分有多少是你写的？"** → 编排、意图/规则引擎、检索链路、拒答策略都是自己写的；**模型是调用的**
48. **"最难的地方在哪？"** → 别答"技术难"，答**定位难**：举"检索通过了却被下游拒答"
49. **"如果重做你会怎么设计？"** → 并行分支、完整 RAG 评测集、可观测
50. **"你觉得这个项目最大的问题是什么？"** → ⭐ **一定要答得出来**（见 §8 软肋）

## 八、你项目里的软肋（面试官会攻击这里）

**提前想好，被问到就不慌。**

| 软肋 | 他会怎么问 | 怎么答 |
|---|---|---|
| **没有 RAG 评测集** | "你怎么知道检索变好了？" | "**这是最大的短板**。我只有 `rag_eval` 脚本和人工抽验，没有标注集。反思重试我是用具体 case 验证的，不是用指标。要补的话我会先标 100 条 query-answer 对。" |
| **无监控告警** | "线上挂了你怎么知道？" | "只有日志和审计表。真实教训是**用户先发现的** —— 这正说明缺监控。" |
| **备份是手工的** | "数据丢了呢？" | "SQLite 单文件，目前靠手工 cp。该上定时任务 + 异地。" |
| **单 worker** | "并发上来怎么办？" | "现在 QPS 很低。单 worker 是为了省内存；要扩得先解决 SQLite 写锁。" |
| **群聊上下文曾串** | "多人群聊会不会串？" | ⭐ "**曾经会**，而且文档还写反了。是我看线上日志才发现的，已按 `发送者:群ID` 隔离。" |
| **报修曾不转人工** | "误判了怎么办？" | ⭐ "**发现过**：报修本来在'跳过置信度确认'的列表里。我把它移出来了 —— 会写库的动作用户识别不准时必须多问一句。" |
| **知识库质量决定效果** | "答得不准怪谁？" | "知识库内容决定上限。我做过一次实测：答案像通用流程而非 XY200 专属，**那是文档的问题，不是检索的**。" |

**主动暴露软肋是加分项** ✗ 因为它说明**你知道自己的系统哪里不行** ✓

## 九、压力问题专项

### "这不就是调 API 加个 prompt 吗？"

> "不是。三个硬区别：
>
> **第一，输出不一样。** 套壳输出文本；我的系统**会真的改数据** ——
> 建工单、按技能/负载派单、建退款单走审批。用户能拿到工单号。
>
> **第二，不知道的时候不一样。** 套壳会编；我的有**双过滤拒答** ——
> 相似度阈值和实体词覆盖两道都不过就明确说'没找到'并引导转人工。
>
> **第三，高风险时不一样。** 套壳直接答；我的会 `interrupt()` **中断等人确认**，
> 状态落盘，跨进程重启还能恢复。
>
> 另外工程上：17 个意图、15 个图节点、112 个接口、27 个权限点、288 个测试。
> 套壳项目通常几十行。"

### "你这个有什么难的？"

> "**难的不是写代码，是定位和取舍。**
>
> 举个真实的：用户问故障码，日志显示检索 `top=0.7185 passed=True` 通过了、
> 命中 15 条，但用户收到的是'知识库里没有记录'。**日志自相矛盾。**
>
> 最后查到是**双重门槛**：generate 节点又按'小标题是否含原因/步骤'过滤了一遍，
> 而文档没有那种小标题，于是过滤结果恒为空 → 拒答。
> 修法是过滤为空时**回退用全部片段**，把该不该答交回 prompt。
>
> 这类问题只有真跑起来才会遇到，而且**检索层是绿的，特别容易误判成'知识库里真没有'**。"

### "如果给你十天，你会改什么？"

| 优先级 | 事项 | 为什么 |
|---|---|---|
| 1 | **建 RAG 评测集**（100 条标注） | 没有指标就无法判断改动是变好还是变坏 |
| 2 | **加监控告警**（错误率、拒答率、延迟 P95） | 现在靠用户反馈发现问题 |
| 3 | 并行分支（`context_collect` ∥ `rule_match`） | 省 30~50% 延迟 |
| 4 | 数据备份自动化 | 目前手工 |
| 5 | 检索失败时的 LLM 兜底工具调用 | 补意图引擎覆盖不到的长尾 |

## 十三、最后三条心法

1. **不要说"我用了 X"，要说"我为什么不用 Y"** —— 取舍才是能力
2. **主动暴露软肋** —— 知道自己系统哪里不行，比假装完美可信得多
3. **失败经历比成功经历值钱** —— 停用词那两个失败方案、那个矛盾日志，
   都是**只有真做过才讲得出来**的细节
